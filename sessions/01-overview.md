# 第1回: 形式手法は何をしているのか

## 自然言語の仕様は穴だらけ

> - 荷主は案件を登録する
> - 案件は、車種が合うドライバーに打診される
> - ドライバーは承諾か辞退をする
> - ドライバーが同時に担当できるのは2件まで

この仕様だけでは、次の問いに答えられない。

- 1件の案件を、複数のドライバーに同時に打診してよいか？
- 「2件まで」は打診中の案件も数えるのか、確定した案件だけか？
- 打診したときは空きがあったが、承諾する前に別の案件が確定したらどうなるか？

実装者はこれを無意識に決めてしまい、人によって決め方が違うのでバグになる。
**曖昧さが残らない言葉（論理）で書けば、こういう穴が機械的に見つかる**というのが形式手法の出発点。

## 仕様は3つの要素でできている

| 要素 | 問い | マッチングの例 |
|---|---|---|
| 状態 | 世界には何があり、どうつながっているか | 案件・ドライバー・車種、誰が何を担当しているか |
| 不変条件 | いつ見ても必ず成り立っていてほしいことは何か | 1案件の担当は1人まで、車種が一致する、担当は2件まで |
| 操作 | 状態はどう変わるか。変わる前に何が必要か | 打診・承諾・辞退・完了・キャンセル |

確かめたい問いは、ほぼ1つに集約される。

> **どの操作をどんな順番で何回やっても、不変条件は壊れないか？**

| ツール | 確かめ方 |
|---|---|
| Alloy | 小さな世界を全パターン探索して、壊れる例を探す（証明ではない） |
| Lean | すべての大きさの世界について、壊れないことを証明する |
| PBT | 実装したコードをランダムに大量に動かして、壊れる例を探す |

## FP の言葉に置き換える

| 形式仕様 | 関数型プログラミング |
|---|---|
| 状態 | 型 |
| 不変条件 | 型で表せるなら型に入れる。無理ならテストか証明で守る |
| 操作 | 関数 `State → State`（失敗しうるなら `State → Result<State>`） |
| 操作の事前条件 | 関数が `Err` を返す条件 |
| 不変条件が壊れない | 正しい値から正しい値しか作らない |

- 「打診中と確定済みが同時に起きない」→ 直和型にすれば表現できなくなる（検査が要らない）
- 「ドライバーごとに担当は2件まで」→ 複数の案件にまたがるので型では表しにくい（PBT / Lean の出番）

2. 案件の状態（打診中・確定・完了など）を TypeScript でどう型にする？
