# 第1回: 形式手法は何をしているのか

## 題材: 案件のダブルブッキング

> - 荷主は案件を登録する
> - 案件は、車種が合う複数のドライバーに一斉に打診される
> - ドライバーは承諾か辞退をする
> - 1つの案件を担当するのは1人のドライバーだけ

この仕様だけでは、次の問いに答えられない。

- 打診された2人が、ほぼ同時に承諾したらどうなるか？
- すでに別の人に決まった案件を承諾しようとしたら、エラーになるのか、無視されるのか？
- 荷主がキャンセルした直後に、ドライバーが承諾したらどうなるか？
- 辞退した人に、もう一度打診してよいか？

実装者はこれを無意識に決めてしまい、人によって決め方が違うのでバグになる。
**曖昧さが残らない言葉（論理）で書けば、こういう穴が機械的に見つかる**というのが形式手法の出発点。

## 仕様は3つの要素でできている

| 要素 | 問い | マッチングの例 |
|---|---|---|
| 状態 | 世界には何があり、どうつながっているか | 案件・ドライバー、誰に打診中か、誰に確定したか |
| 不変条件 | いつ見ても必ず成り立っていてほしいことは何か | **1案件の担当は1人まで**、担当者の車種が合っている |
| 操作 | 状態はどう変わるか。変わる前に何が必要か | 打診・承諾・辞退・完了・キャンセル |

確かめたい問いは、ほぼ1つに集約される。

> **どの操作をどんな順番で何回やっても、不変条件は壊れないか？**

## 検査と証明の違い

| 方法 | ツール例 | 保証 | 手間 |
|---|---|---|---|
| ランダムテスト | PBT（fast-check, QuickCheck） | たまたま試した入力について | 小 |
| 範囲を区切った全探索 | **Alloy**、TLA+ の TLC | 指定した大きさの中は全部 | 小〜中 |
| 自動証明 | Dafny、Why3（中で SMT ソルバーが動く） | 全部（自動で解けたら） | 中 |
| 対話的証明 | **Lean**、Rocq（旧 Coq）、Isabelle、Agda | 全部 | 大（人が証明を書く） |

- Alloy は `check ... for 1 Driver` のように世界の大きさを区切って全探索する。
  ダブルブッキングには2人必要なので、**ドライバー1人の世界では絶対に見つからない**（Alloy は「反例なし」と答える）。
  「反例なし」は「その大きさまでには無い」という意味でしかない。
- それでも役立つのは「仕様のバグのほとんどは小さな世界で再現する」（small scope hypothesis）から。
  ダブルブッキングも、ドライバー2人・案件1件で再現する。
- 証明は、どんな大きさの世界でも成り立つことを帰納法で示す。
  1. 最初の状態で不変条件が成り立つ
  2. 不変条件が成り立つどんな状態から、どの操作をしても、また成り立つ
  → 何回操作しても永遠に成り立つ

## FP の言葉に置き換える

| 形式仕様 | 関数型プログラミング |
|---|---|
| 状態 | 型 |
| 不変条件 | 型で表せるなら型に入れる。無理ならテストか証明で守る |
| 操作 | 関数 `State → State`（失敗しうるなら `State → Result<State>`） |
| 操作の事前条件 | 関数が `Err` を返す条件 |
| 不変条件が壊れない | 正しい値から正しい値しか作らない |

予告: 案件の状態を直和型にして「確定」状態にドライバーを1人だけ持たせれば、
**「2人が担当している状態」は型の上で表現できなくなる**。
ではダブルブッキングは型だけで完全に防げるのか？ → 実は防げない。
2人目の承諾で担当者が**黙って上書きされる**という形で戻ってくる（1人目は自分が担当だと思ったまま）。
型は「おかしな状態」を消せるが、「おかしな状態遷移」までは消せない。ここが PBT と Lean の出番になる。
